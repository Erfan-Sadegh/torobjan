# ترب جان: معماری محصول، مسیر افزودن محصول، و طرح آپدیت قیمت

این سند برای آنبورد شدن محصولی و فنی روی ترب جان نوشته شده است. مخاطب اصلی آن کسی است که توسعه دهنده نیست، اما می خواهد بتواند در یک جلسه جدی با CTO، تیم فنی، یا سرمایه گذار توضیح بدهد محصول چطور کار می کند، چرا این طراحی انتخاب شده، چه چیزهایی آماده است، و مسیر توسعه بعدی چیست.

آخرین وضعیت این سند: 2026-06-16

## خلاصه اجرایی

ترب جان ابزاری است برای فروشنده های حضوری که تعداد محصول زیاد دارند و نمی خواهند محصولاتشان را دانه دانه در پنل ترب ثبت کنند.

محصول فعلی دو مسیر اصلی برای ورود محصول دارد:

1. آپلود فایل اکسل
2. خواندن محصولات از کانال ایتا

بعد از ورود محصولات، سیستم آن ها را با محصولات پایه ترب تطبیق می دهد. فروشنده نتیجه را بررسی می کند، قیمت نهایی را تایید یا اصلاح می کند، و در نهایت یک ثبت یا batch ساخته می شود. ادمین بعدا همان batch را با endpoint bulk ترب به فروشگاه ترب ارسال می کند.

قابلیت بعدی که طراحی می کنیم، آپدیت قیمت است:

1. فروشنده قبلا محصولاتی را وارد ترب کرده است.
2. بعدا فایل اکسل جدید یا پست های جدید/ویرایش شده ایتا می آید.
3. سیستم تشخیص می دهد قیمت کدام محصولات قبلی تغییر کرده است.
4. قبل از ارسال، یک preview به کاربر نشان داده می شود.
5. بعد از تایید کاربر، فقط تغییرات قیمت آماده ارسال به ترب می شود.

ارسال واقعی آپدیت قیمت به ترب وابسته به این است که endpoint ترب رفتار upsert داشته باشد:

```text
اگر محصول با shop_id + base_product_rk در فروشگاه نبود، ساخته شود.
اگر بود، قیمتش به روز شود.
```

## واژه های کلیدی

### shop_id

شناسه فروشگاه در ترب است. بدون `shop_id` اساسا نمی دانیم محصول باید وارد کدام فروشگاه شود.

### base_prk / base_product_rk

شناسه محصول پایه در ترب است. مثلا «رب گوجه روژین ۸۰۰ گرم» یک محصول پایه در ترب دارد و با `base_prk` مشخص می شود.

نکته مهم:

```text
base_prk به تنهایی کافی نیست.
shop_id + base_prk یعنی این محصول خاص در این فروشگاه خاص.
```

مثال:

```text
shop_id=411488 + base_prk=abc
```

یعنی محصول `abc` در فروشگاه `411488`.

### batch

هر بار که فروشنده بخشی از محصولات را تایید می کند، یک batch ساخته می شود.

مثال:

```text
Batch 1: فروشنده امروز 50 محصول را تایید کرد.
Batch 2: فروشنده فردا 30 محصول دیگر را تایید کرد.
```

Batch برای این است که ادمین بتواند همان بخش مشخص را دانلود یا به ترب ارسال کند، بدون اینکه محصولات قبلی دوباره ارسال شوند.

### BatchItem

هر محصول داخل یک batch یک BatchItem است.

مثال:

```text
Batch 1
  BatchItem 1: رب روژین، قیمت 120000
  BatchItem 2: شامپو صحت، قیمت 85000
```

در طراحی آینده، وضعیت ارسال هر BatchItem جدا ذخیره می شود.

### Preview

Preview یعنی «پیشنهاد تغییر قبل از اجرا».

در آپدیت قیمت، سیستم نباید بدون تایید فروشنده چیزی را به ترب بفرستد. اول باید بگوید:

```text
من فکر می کنم قیمت این محصولات تغییر کرده است.
این ها را بررسی و تایید کن.
```

Preview در دیتابیس ذخیره می شود تا اگر صفحه refresh شد، اینترنت قطع شد، یا کاربر بعدا برگشت، نتیجه بررسی از بین نرود.

Preview ارسال به ترب نیست. فقط یک پیش نویس قابل بررسی است.

## راهنمای خیلی پایه برای خواننده غیر فنی

این بخش برای این است که اگر کسی برنامه نویس نیست، با واژه های فنی سند گم نشود.

### دیتابیس چیست؟

دیتابیس مثل دفتر ثبت رسمی محصول است. هر چیزی که نباید با refresh صفحه یا خاموش شدن برنامه از بین برود، باید در دیتابیس ذخیره شود.

مثلا:

```text
نام فروشگاه
محصولات خوانده شده از اکسل
نتایج پیشنهادی ترب
انتخاب های فروشنده
ثبت های مرحله ای
وضعیت ارسال به ترب
```

اگر چیزی فقط در صفحه مرورگر باشد و در دیتابیس ذخیره نشده باشد، با بستن صفحه ممکن است از بین برود.

### جدول چیست؟

جدول مثل یک شیت اکسل داخل دیتابیس است.

مثلا جدول `submissions` شبیه این است:

```text
id | store_name        | source | status
1  | سوپرمارکت بهار   | excel  | ready
2  | فروشگاه کوثر     | eitaa  | submitted
```

هر خط در جدول را «ردیف» یا row می گوییم.

### API چیست؟

API یعنی راه رسمی حرف زدن دو نرم افزار با هم.

مثلا ترب جان به ترب می گوید:

```text
این محصول ها را برای این فروشگاه اضافه کن.
```

این درخواست از طریق API ترب فرستاده می شود.

### endpoint چیست؟

Endpoint یعنی آدرس دقیق یک کار در API.

مثلا:

```text
https://api.torob.com/panel/offline-shop/product-in-store/searched/bulk-add/
```

این endpoint برای اضافه کردن دسته جمعی محصول به فروشگاه ترب است.

### token چیست؟

Token مثل کلید ورود است. اگر token درست نباشد، API اجازه کار نمی دهد.

توکن Uniom یعنی کلیدی که به ما اجازه می دهد از طرف اکانت متصل شده، پیام های ایتا را بخوانیم.

### getUpdates چیست؟

`getUpdates` یک endpoint در مدل Bot API است.

کارش این است که بپرسد:

```text
از آخرین باری که پرسیدم، چه اتفاق جدیدی افتاده؟
```

مثلا ممکن است جواب بدهد:

```text
یک پست جدید در کانال آمد.
یک پست قبلی ویرایش شد.
```

در مسیر آپدیت ایتا، ما از `getUpdates` برای پیدا کردن پست های جدید یا ویرایش شده استفاده می کنیم.

فرق آن با `getChatHistory`:

```text
getChatHistory: برو تاریخچه پیام های کانال را بخوان.
getUpdates: بگو از آخرین بار چه اتفاق جدیدی رخ داده.
```

برای ایمپورت اولیه، `getChatHistory` مناسب تر است.

برای آپدیت های بعدی، `getUpdates` مناسب تر است.

### long polling چیست؟

Long polling یعنی سیستم ما از Uniom می پرسد:

```text
اگر اتفاق جدیدی داری، همین الان بده.
اگر نداری، چند ثانیه صبر کن؛ شاید در همین چند ثانیه اتفاق جدیدی رسید.
اگر باز هم چیزی نرسید، جواب خالی بده.
```

این با polling ساده فرق دارد.

Polling ساده یعنی مثلا هر ۵ ثانیه یک درخواست خیلی کوتاه بزنیم:

```text
چیزی هست؟
نه.
۵ ثانیه بعد...
چیزی هست؟
نه.
۵ ثانیه بعد...
چیزی هست؟
بله.
```

Long polling یعنی هر درخواست می تواند چند ثانیه باز بماند:

```text
چیزی هست؟ اگر نیست تا ۳۰ ثانیه صبر کن.
...
در ثانیه ۱۲ یک پست جدید آمد.
Uniom همان لحظه جواب می دهد.
```

چرا این بهتر است؟

1. تعداد درخواست های بیهوده کمتر می شود.
2. اگر پست جدید بیاید، معمولا زودتر از polling ساده متوجه می شویم.
3. برای سیستم آپدیت ایتا، لازم نیست هر لحظه با فشار زیاد تاریخچه کانال را بخوانیم.

مثال خیلی ساده:

```text
getUpdates(timeout=30, offset=103)
```

یعنی:

```text
از update شماره ۱۰۳ به بعد را بده.
اگر الان چیزی نداری، حداکثر ۳۰ ثانیه منتظر بمان.
```

اگر در این ۳۰ ثانیه پست جدید یا ویرایش پست برسد، Uniom همان را برمی گرداند.

اگر هیچ اتفاقی نیفتد، جواب تقریبا این شکلی است:

```json
{
  "ok": true,
  "result": []
}
```

نکته مهم: جواب خالی همیشه خطا نیست. گاهی فقط یعنی در این بازه اتفاق جدیدی نیفتاده است.

### update چیست؟

Update یعنی یک رویداد جدید.

مثلا:

```text
update_id=100
type=channel_post
message_id=500
```

یعنی یک پست جدید در کانال آمده است.

یا:

```text
update_id=101
type=edited_channel_post
message_id=500
```

یعنی همان پست قبلی ویرایش شده است.

### allowed_updates چیست؟

`allowed_updates` یعنی به Uniom بگوییم فقط چه نوع اتفاق هایی را می خواهیم.

برای ما فعلا این دو مهم است:

```text
channel_post
edited_channel_post
```

یعنی:

```text
پست جدید کانال
پست ویرایش شده کانال
```

چرا محدود می کنیم؟

چون شاید API انواع دیگری هم داشته باشد، مثل پیام خصوصی، عضویت، یا چیزهای دیگر. ما برای آپدیت قیمت فقط پست کانال و ویرایش پست کانال را می خواهیم.

### offset و last_update_id چیست؟

هر update یک شماره دارد.

مثال:

```text
update_id=100
update_id=101
update_id=102
```

اگر ما آخرین update موفق را `102` ذخیره کرده باشیم، دفعه بعد می گوییم:

```text
offset=103
```

یعنی:

```text
از 103 به بعد را بده، قبلی ها را دیده ام.
```

اگر offset را زود جلو ببریم، ممکن است یک update را از دست بدهیم. برای همین اول preview را ذخیره می کنیم، بعد `last_update_id` را جلو می بریم.

یک مثال واقعی تر:

```text
آخرین update ذخیره شده در دیتابیس: 102
درخواست بعدی ما: getUpdates(offset=103)
Uniom جواب می دهد:
  update_id=103
  update_id=104
```

سیستم باید اول updateهای ۱۰۳ و ۱۰۴ را تبدیل به preview کند و در دیتابیس ذخیره کند.

بعد از اینکه ذخیره موفق شد:

```text
last_update_id = 104
```

اگر وسط کار خطا شد، `last_update_id` را جلو نمی بریم. دفعه بعد دوباره از `103` می خوانیم. شاید یک update دوباره بررسی شود، ولی update از دست نمی رود. برای MVP این رفتار بهتر از این است که قیمت جدید فروشنده را گم کنیم.

### httpx چیست؟

`httpx` یک کتابخانه پایتون است برای درخواست زدن به APIها.

یعنی وقتی می خواهیم از کد پایتون به Uniom یا ترب درخواست بزنیم، از `httpx` استفاده می کنیم.

مثال مفهومی:

```text
httpx برو به Uniom بگو getUpdates را بده.
Uniom جواب JSON برمی گرداند.
ما جواب را تحلیل می کنیم.
```

چرا برای Uniom فعلا SDK تلگرام نیاوردیم؟

چون با `httpx` مستقیم، کار ساده تر و قابل کنترل تر است. پروژه همین حالا هم برای Uniom یک client اختصاصی دارد. پس به جای اضافه کردن dependency جدید، همان client را کامل تر می کنیم.

## معماری فعلی در یک نگاه

کد اصلی مدل داده در این فایل است:

```text
app/models.py
```

مدل فعلی:

```text
Submission
 ├── SubmissionRow
 │    ├── TorobMatch
 │    └── SubmissionSelection
 └── SubmissionBatch
      └── SubmissionBatchItem
```

### Submission

Submission یعنی یک نوبت ورود محصول توسط فروشنده.

مثال ها:

```text
فروشنده فایل اکسل آپلود می کند.
فروشنده کانال ایتا معرفی می کند.
```

هر کدام یک Submission می سازند.

فیلدهای مهم:

```text
store_name
seller_phone
shop_id
source: excel یا eitaa
source_ref: مثلا آیدی کانال ایتا
status
total_rows
selected_rows
```

وضعیت های فعلی:

```text
processing: سیستم در حال پردازش و جستجو است.
ready: نتیجه آماده بررسی کاربر است.
failed: پردازش با خطا متوقف شده است.
submitted: کاربر مرحله را نهایی کرده است.
```

نکته مهم:

```text
submitted یعنی کاربر تایید کرده، نه اینکه حتما به ترب ارسال شده باشد.
```

### SubmissionRow

SubmissionRow یعنی یک محصول ورودی.

در اکسل، هر ردیف محصول یک SubmissionRow است.

در ایتا، هر محصول استخراج شده از پیام ها یک SubmissionRow است.

فیلدهای مهم:

```text
input_product_name
input_price
barcode
brand
description
source_message_id
source_image_path
auto_match_score
final_price
submitted_at
```

### TorobMatch

TorobMatch یعنی یک گزینه پیشنهادی از ترب.

مثلا کاربر در اکسل نوشته:

```text
رب گوجه
```

سیستم در ترب جستجو می کند و چند نتیجه پیدا می کند:

```text
رب گوجه روژین ۸۰۰ گرم
رب گوجه چین چین ۸۰۰ گرم
رب گوجه طبیعت ۷۰۰ گرم
```

هر کدام یک TorobMatch می شود.

فیلدهای مهم:

```text
base_prk
name
price
image_url
source: torob یا torob_image
rank
```

### SubmissionSelection

SubmissionSelection انتخاب فعلی کاربر است.

مثال:

```text
ردیف اکسل: رب گوجه
انتخاب کاربر: رب گوجه روژین ۸۰۰ گرم
قیمت نهایی: 120000
```

این انتخاب با autosave ذخیره می شود. یعنی کاربر اگر صفحه را refresh کند، انتخاب ها از بین نمی روند.

### SubmissionBatch

وقتی کاربر دکمه تایید را می زند، یک batch ساخته می شود.

Batch یعنی یک ثبت مرحله ای.

### SubmissionBatchItem

BatchItem نسخه ثابت شده انتخاب کاربر در لحظه تایید است.

چرا مهم است؟

چون Selection ممکن است بعدا تغییر کند، ولی BatchItem باید نشان دهد در آن لحظه دقیقا چه چیزی ثبت شده بود.

## مسیر فعلی افزودن محصول با اکسل

### مرحله 1: فروشنده فایل را وارد می کند

فروشنده وارد مسیر اکسل می شود و این اطلاعات را می دهد:

```text
نام فروشگاه
شماره موبایل اختیاری
فایل اکسل
```

سیستم ستون های رایج را تشخیص می دهد، مثلا:

```text
product_name
نام کالا
نام محصول
محصول
price
قیمت
فی
barcode
بارکد
brand
برند
```

### مرحله 2: Submission و Row ساخته می شود

برای کل فایل یک Submission ساخته می شود.

برای هر محصول داخل فایل یک SubmissionRow ساخته می شود.

### مرحله 3: جستجو در ترب

برای هر محصول، سیستم در ترب جستجو می کند.

نتایج در TorobMatch ذخیره می شوند.

در صفحه فروشنده، ابتدا چند گزینه محدود نمایش داده می شود. اگر لازم بود، کاربر می تواند گزینه های بیشتری بگیرد.

### مرحله 4: فروشنده انتخاب می کند

فروشنده برای هر ردیف، محصول درست را انتخاب می کند و قیمت نهایی را تایید یا اصلاح می کند.

در مسیر اکسل، چون ممکن است قیمت فایل به ریال یا تومان باشد، از کاربر واحد قیمت پرسیده می شود.

### مرحله 5: Autosave

انتخاب ها و قیمت ها در SubmissionSelection ذخیره می شوند.

هدف:

```text
کاربر مجبور نباشد همه محصولات را یکجا تمام کند.
اگر وسط کار رفت و برگشت، انتخاب ها باقی بماند.
```

### مرحله 6: تایید و ساخت Batch

وقتی کاربر دکمه تایید را می زند، سیستم از انتخاب های فعلی Batch می سازد.

هر انتخاب تبدیل به SubmissionBatchItem می شود.

### مرحله 7: ادمین Shop ID را ذخیره می کند

ادمین وارد پنل می شود و Shop ID فروشگاه ترب را روی Submission ذخیره می کند.

### مرحله 8: ارسال به ترب

ادمین روی batch کلیک می کند و سیستم به endpoint bulk ترب درخواست می زند.

در حال حاضر هر درخواست حداکثر 100 محصول دارد.

برای 300 محصول:

```text
Request 1: 100 item
Request 2: 100 item
Request 3: 100 item
```

## مسیر فعلی افزودن محصول با ایتا

### مرحله 1: فروشنده کانال ایتا را می دهد

فروشنده آیدی کانال ایتا را وارد می کند.

مثال:

```text
@kosarmarket
```

### مرحله 2: Uniom تاریخچه کانال را می خواند

سیستم از Uniom استفاده می کند.

فعلا برای ایمپورت اولیه از این مسیر استفاده می شود:

```text
getChat
getChatHistory
getFile
downloadFile
```

یعنی:

1. مطمئن می شویم کانال وجود دارد.
2. پیام های اخیر کانال را می خوانیم.
3. محصول و قیمت را از متن یا کپشن استخراج می کنیم.
4. اگر عکس وجود داشت، عکس را می گیریم.

### مرحله 3: parser محصول را استخراج می کند

Parser یعنی کدی که متن پیام را می خواند و محصول و قیمت را درمی آورد.

مثال:

```text
رب گوجه روژین ۸۰۰ گرم
قیمت ۹۵
```

سیستم این را تبدیل می کند به:

```text
نام محصول: رب گوجه روژین ۸۰۰ گرم
قیمت: 95000 تومان
```

قانون قیمت در ایتا:

```text
اگر ریال نوشته شده باشد، تقسیم بر 10 می شود.
اگر عدد کوچک مثل 95 باشد، 95000 تومان فرض می شود.
اگر عدد بزرگ مثل 1200000 باشد، 1200000 تومان فرض می شود.
```

در مسیر ایتا، قیمت ها در سیستم همیشه تومان هستند. بنابراین دیگر از کاربر ریال/تومان پرسیده نمی شود.

### مرحله 4: تطبیق با ترب

برای هر محصول ایتا، سیستم دو نوع جستجو انجام می دهد:

1. جستجوی متنی در ترب
2. در صورت وجود عکس، جستجوی تصویری در ترب

نتایج متنی و تصویری با هم ترکیب می شوند.

اگر سیستم با امتیاز کافی مطمئن باشد، یک گزینه را از قبل انتخاب می کند.

اگر مطمئن نباشد، محصول به بخش «نیازمند بررسی» می رود.

### مرحله 5: Preview انتخاب ایتا

بعد از پردازش، فروشنده صفحه بررسی را می بیند:

```text
محصولات آماده تایید
محصولات نیازمند بررسی
```

فروشنده می تواند قیمت را اصلاح کند یا انتخاب محصول را عوض کند.

### مرحله 6: تایید و Batch

مثل مسیر اکسل، بعد از تایید، batch ساخته می شود.

## چرا برای ایتا SDK تلگرام نیاوردیم؟

سازنده Uniom گفت:

```text
مثل ربات های تلگرام رفتار کن.
کلاینت تلگرام است، پشت آن اکانت ایتا است.
با توکن Uniom و base URL Uniom کار کن.
```

ما دو گزینه داریم:

1. استفاده از SDK تلگرام
2. درخواست مستقیم HTTP به Uniom

فعلا گزینه دوم بهتر است.

چرا؟

1. پروژه همین حالا UniomClient اختصاصی دارد.
2. با HTTP مستقیم، dependency جدید اضافه نمی شود.
3. تست نوشتن ساده تر است.
4. کنترل timeout، retry، و خطاها دست خودمان است.
5. معلوم نیست SDK تلگرام با base URL و رفتار Uniom صد درصد بدون دردسر کار کند.

پس کار ما این نیست که SDK را دور بزنیم؛ بلکه چون API Uniom شبیه Bot API است، همان مسیر را با HTTP مستقیم و کنترل بیشتر استفاده می کنیم.

## تستی که روی Uniom انجام شد

با توکن تست، این endpointها بررسی شدند:

```text
getUpdates
getWebhookInfo
getMe
getChat
getChatHistory
```

### تست اولیه

در تست اولیه، `getUpdates` در دسترس بود اما update جدیدی برنمی گرداند:

```text
getUpdates: 200 OK
ok: true
result: []
```

یعنی endpoint در دسترس است، اما آن لحظه آپدیت جدیدی در صف نبود.

نتیجه getWebhookInfo:

```text
url: ""
pending_update_count: 0
allowed_updates: ["channel_post", "edited_channel_post"]
```

معنی:

1. webhook فعال نیست.
2. long polling قابل استفاده است.
3. Uniom برای همین token انتظار channel_post و edited_channel_post را دارد.

نتیجه getChatHistory برای کانال نمونه:

```text
message_id برگشت.
caption برگشت.
photo برگشت.
```

پس برای ایمپورت اولیه، مسیر فعلی درست کار می کند.

برای اثبات نهایی `getUpdates` باید در کانال تست یک پست جدید یا یک ویرایش واقعی انجام شود.

### تست تکمیلی با کانال @regaal

برای بررسی عملی تر، در کانال `@regaal` پست جدید و ویرایش انجام شد.

در یک مرحله، `getChatHistory` پست جدید را می دید، اما `getUpdates` هنوز خالی بود. این یعنی دسترسی به تاریخچه کانال وجود داشت، ولی update stream هنوز فعال یا آماده نبود.

بعد از اصلاح Uniom توسط سازنده، تست دوباره انجام شد.

نتیجه جدید:

```text
getUpdates: 200 OK
ok: true
result:
  update_id: 84
  type: channel_post
  message_id: 124
  chat_username: regaal
  has_text: true
```

یعنی `getUpdates` حالا پست جدید کانال را واقعا برمی گرداند.

بعد از یک ویرایش جدید روی همان پست، دوباره تست شد:

```text
getUpdates: 200 OK
ok: true
result:
  update_id: 85
  type: edited_channel_post
  message_id: 124
  chat_username: regaal
  has_text: true
  edit_date: 1781682789
```

یعنی Uniom هم پست جدید کانال را می دهد و هم ویرایش همان پست را.

در همان تست، `getWebhookInfo` هم این را نشان داد:

```text
url: ""
pending_update_count: 13
allowed_updates: ["channel_post", "edited_channel_post", "edited_message", "message"]
```

معنی:

1. webhook فعال نیست، پس long polling مسیر درست است.
2. Uniom حالا `channel_post` را وارد صف `getUpdates` می کند.
3. برای پیاده سازی واقعی باید `offset` ذخیره شود، وگرنه همان update ممکن است چند بار دیده شود.

در همین تست، `getChatHistory` برای `@regaal` هم همان پست های کانال را می دید:

```text
message_id: 124
has_text: true
has_photo: false
```

پس وضعیت فعلی:

```text
getChatHistory برای ایمپورت اولیه کار می کند.
getUpdates برای تشخیص پست جدید کانال کار می کند.
getUpdates برای تشخیص ویرایش پست کانال هم کار می کند.
```

نکته درباره SDK:

اگر SDK تلگرام فقط همین endpoint را صدا بزند، از نظر خروجی تفاوت بنیادی ندارد. تفاوت اصلی SDK این است که loop، offset، و long polling را آماده تر مدیریت می کند. ما می توانیم برای MVP با `httpx` همین رفتار را مستقیم بسازیم، چون کنترل و تست پذیری بیشتری داریم. اگر بعدا دیدیم SDK Uniom رفتار اختصاصی یا پایدارتری دارد، می توانیم client را عوض کنیم بدون اینکه منطق محصول را عوض کنیم.

## طراحی آپدیت قیمت با ایتا

### هدف

فروشنده ممکن است در کانال ایتا قیمت ها را تغییر دهد. ما می خواهیم این تغییرات را تشخیص بدهیم و به او بگوییم:

```text
این قیمت ها نسبت به قبل تغییر کرده اند. تایید می کنی برای ترب آماده شوند؟
```

### نسخه اول: on-demand

در نسخه اول worker دائمی نمی سازیم.

یعنی سیستم خودکار همیشه در حال گوش دادن به کانال نیست.

فروشنده یا ادمین دکمه می زند:

```text
بررسی قیمت های جدید ایتا
```

همان لحظه سیستم getUpdates را صدا می زند.

چرا on-demand؟

1. ساده تر است.
2. نیاز به زیرساخت worker ندارد.
3. ریسک پردازش همزمان کمتر است.
4. برای MVP کافی است.

### long polling در نسخه on-demand چطور کار می کند؟

در نسخه on-demand، سیستم همیشه پشت صحنه روشن نیست که کانال را گوش کند.

فروشنده یا ادمین دکمه می زند:

```text
بررسی قیمت های جدید ایتا
```

بعد سیستم این کارها را انجام می دهد:

```text
1. از دیتابیس می خواند آخرین update پردازش شده چند بوده.
2. مثلا می بیند last_update_id = 102.
3. به Uniom درخواست می زند:
   getUpdates(offset=103, timeout=30)
4. Uniom اگر update آماده داشته باشد، سریع جواب می دهد.
5. اگر update آماده نداشته باشد، تا ۳۰ ثانیه منتظر می ماند.
6. اگر پست جدید یا ادیت جدید برسد، همان را برمی گرداند.
7. اگر هیچ اتفاقی نیفتد، result خالی برمی گرداند.
```

برای فروشنده، این یعنی سیستم بدون فشار اضافه بررسی می کند آیا کانال از دفعه قبل تغییری داشته یا نه.

چرا به جای `getChatHistory` برای آپدیت از `getUpdates` استفاده می کنیم؟

```text
getChatHistory:
  هر بار بخشی از تاریخچه کانال را دوباره می خواند.
  برای ایمپورت اولیه خوب است.
  برای آپدیت های مکرر ممکن است کار تکراری زیاد بسازد.

getUpdates:
  فقط اتفاق های جدید از دفعه قبل را می دهد.
  برای آپدیت قیمت مناسب تر است.
  نیاز دارد offset/last_update_id را درست ذخیره کنیم.
```

پس برای آپدیت قیمت، اصل طراحی این است:

```text
اولین بار: getChatHistory برای ساختن محصول های اولیه.
بعد از آن: getUpdates برای دیدن پست ها و ادیت های جدید.
```

### last_update_id چیست؟

هر update در Uniom یک شماره دارد:

```text
update_id=100
update_id=101
update_id=102
```

ما باید آخرین update پردازش شده را نگه داریم.

مثال:

```text
آخرین update پردازش شده: 102
```

دفعه بعد می گوییم:

```text
از 103 به بعد را بده.
```

اگر این عدد را ذخیره نکنیم، ممکن است یک update را چند بار بررسی کنیم.

اگر این عدد را خیلی زود جلو ببریم، ممکن است یک update را از دست بدهیم.

قانون درست:

```text
اول preview را با موفقیت ذخیره کن.
بعد last_update_id را جلو ببر.
```

### Preview آپدیت ایتا دقیقا چیست؟

Preview یعنی لیست تغییرات پیشنهادی قبل از اجرا.

مثال:

```text
رب روژین ۸۰۰ گرم
قیمت قبلی: 95000
قیمت جدید: 110000
منبع: ویرایش پست ایتا
```

این preview باید در دیتابیس ذخیره شود.

چرا؟

1. اگر کاربر refresh کند، اطلاعات از بین نرود.
2. اگر وسط کار اینترنت قطع شود، دوباره مجبور نشویم همه چیز را از Uniom بخوانیم.
3. اگر سیستم خطا داد، last_update_id را جلو نبریم و بتوانیم دوباره بررسی کنیم.
4. کاربر بتواند مثل مسیر افزودن محصول، بعدا برگردد و ادامه دهد.

برای ذخیره preview می توانیم از همان مفهوم Submission استفاده کنیم، اما با operation متفاوت.

پیشنهاد:

```text
Submission.operation = add یا price_update
```

و برای هر تغییر قیمت یک SubmissionRow ساخته شود.

در این حالت:

```text
input_product_name: نام محصول از ایتا
input_price: قیمت جدید
final_price: قیمت جدید پیشنهادی
source_message_id: شناسه پیام ایتا
TorobMatch: محصول ترب قبلی یا گزینه های احتمالی
SubmissionSelection: انتخاب پیشنهادی اگر تطبیق مطمئن است
```

### Preview در کدام جدول دیتابیس ذخیره می شود؟

برای اینکه سیستم ساده بماند، preview آپدیت قیمت را با همان جدول های فعلی ذخیره می کنیم، نه با یک سیستم کاملا جدا.

یعنی:

```text
Submission
SubmissionRow
TorobMatch
SubmissionSelection
```

اما باید یک فیلد جدید به Submission اضافه شود:

```text
operation
```

مقدارهای پیشنهادی:

```text
add
price_update
```

قبل از این تغییر، Submission فقط می گوید من از کدام منبع آمده ام:

```text
source = excel یا eitaa
```

بعد از این تغییر، Submission دو چیز را می گوید:

```text
source = excel یا eitaa
operation = add یا price_update
```

یعنی می فهمیم:

```text
این Submission از ایتا آمده و برای افزودن محصول است.
یا از ایتا آمده و برای آپدیت قیمت است.
یا از اکسل آمده و برای افزودن محصول است.
یا از اکسل آمده و برای آپدیت قیمت است.
```

#### قبل از ذخیره preview

فرض کنیم قبلا فروشنده این محصول را اضافه کرده است:

```text
Submission قبلی
  SubmissionRow:
    input_product_name = رب روژین ۸۰۰ گرم
    source_message_id = 500
    final_price = 95000
    selected TorobMatch:
      base_prk = abc
```

بعد در ایتا پیام ویرایش می شود:

```text
message_id = 500
رب روژین ۸۰۰ گرم
قیمت 110000
```

در این لحظه هنوز هیچ چیزی برای آپدیت در دیتابیس نداریم. فقط Uniom به ما گفته یک تغییر جدید هست.

#### بعد از ذخیره preview

یک Submission جدید از نوع آپدیت ساخته می شود:

```text
Submission
  source = eitaa
  operation = price_update
  status = ready
```

داخل آن یک ردیف ساخته می شود:

```text
SubmissionRow
  input_product_name = رب روژین ۸۰۰ گرم
  input_price = 110000
  final_price = 110000
  source_message_id = 500
```

و چون محصول قبلی را می شناسیم، همان محصول ترب به عنوان گزینه انتخاب شده ذخیره می شود:

```text
TorobMatch
  base_prk = abc
  name = رب روژین ۸۰۰ گرم

SubmissionSelection
  match = abc
  final_price = 110000
```

این یعنی سیستم هنوز به ترب چیزی نفرستاده؛ فقط گفته:

```text
من پیشنهاد می کنم قیمت محصول abc از 95000 به 110000 تغییر کند.
```

#### چرا preview را ذخیره می کنیم؟

اگر preview فقط در حافظه یا صفحه مرورگر باشد:

```text
کاربر صفحه را refresh کند، همه چیز از بین می رود.
اینترنت قطع شود، دوباره باید getUpdates بخوانیم.
اگر offset جلو رفته باشد، ممکن است update را دوباره نبینیم.
```

پس preview را در دیتابیس ذخیره می کنیم تا:

```text
قابل ادامه دادن باشد.
قابل بررسی توسط کاربر باشد.
قابل audit باشد.
بعدا بتوان از همان preview BatchItem ساخت.
```

#### چه زمانی last_update_id جلو می رود؟

بعد از اینکه Submission آپدیت و ردیف های preview با موفقیت ذخیره شدند.

نه قبلش.

چرا؟

چون اگر قبل از ذخیره preview بگوییم update را پردازش کردیم، ولی وسط کار خطا بخوریم، ممکن است آن update از دست برود.

### تطبیق در آپدیت ایتا

دو حالت داریم.

#### حالت 1: message_id شناخته شده است

قبلا این پیام را دیده بودیم:

```text
message_id=500
رب روژین ۸۰۰ گرم
قیمت 95000
```

بعد همان پیام ویرایش می شود:

```text
message_id=500
رب روژین ۸۰۰ گرم
قیمت 110000
```

اینجا تطبیق ساده است:

```text
این همان محصول قبلی است.
```

پس سیستم مستقیم یک update candidate می سازد.

#### حالت 2: message_id جدید است

فروشنده پست جدید گذاشته:

```text
message_id=800
رب روژین ۸۰۰ گرم
قیمت 110000
```

اینجا باید بین محصولات قبلی همان فروشگاه بگردیم.

اگر محصول قبلی دقیق یا بسیار نزدیک پیدا شد، می توانیم آن را پیشنهاد دهیم.

مثال:

```text
گزینه 1: رب روژین ۸۰۰ گرم
گزینه 2: رب روژین ۴۰۰ گرم
گزینه 3: رب طبیعت ۸۰۰ گرم
```

در این مثال گزینه اول دقیقا همان محصول است. پس اگر امتیاز شباهت خیلی بالا باشد و فاصله خوبی با گزینه دوم داشته باشد، می توان آن را به صورت پیش فرض انتخاب کرد.

اما اگر این طور باشد:

```text
گزینه 1: رب روژین ۸۰۰ گرم
گزینه 2: رب روژین ۸۵۰ گرم
گزینه 3: رب روژین ویژه ۸۰۰ گرم
```

ممکن است اشتباه شود. این می رود به بخش نیازمند بررسی.

قانون پیشنهادی:

```text
اگر match دقیق یا امتیاز خیلی بالا بود، پیش فرض انتخاب شود.
اگر چند گزینه نزدیک بودند، کاربر بررسی کند.
```

### صفحه preview آپدیت ایتا

صفحه پیشنهادی:

```text
بررسی قیمت های جدید ایتا
```

بالا:

```text
۱۲ تغییر قیمت پیدا شد
۵ مورد نیازمند بررسی
۲۴ محصول بدون تغییر
```

بخش اول: آماده تایید

```text
رب روژین ۸۰۰ گرم
قیمت قبلی: 95,000 تومان
قیمت جدید: 110,000 تومان
منبع: ویرایش پست ایتا
```

کاربر می تواند:

```text
تیک را بردارد
قیمت جدید را اصلاح کند
```

بخش دوم: نیازمند بررسی

```text
متن کانال:
رب روژین ویژه ۸۰۰ گرم - ۱۱۰

گزینه های احتمالی:
رب روژین ۸۰۰ گرم
رب روژین ۴۰۰ گرم
رب طبیعت ۸۰۰ گرم
```

کاربر محصول درست را انتخاب می کند.

دکمه نهایی:

```text
تایید و آماده سازی ۱۲ آپدیت قیمت
```

تا زمانی که Upsert ترب آماده نشده، این دکمه فقط batch آپدیت را آماده می کند، نه ارسال واقعی.

## طراحی آپدیت قیمت با اکسل

مسیر اکسل برای آپدیت ساختارمندتر از ایتا است.

فروشنده فایل اکسل جدید می دهد.

سیستم باید محصولات داخل اکسل را با محصولاتی که قبلا برای همان فروشگاه ارسال شده اند مقایسه کند.

### هدف

```text
فقط قیمت محصولاتی را آپدیت کنیم که قبلا در همین فروشگاه وارد ترب شده اند و قیمتشان تغییر کرده است.
```

### جریان پیشنهادی

```text
انتخاب فروشگاه
انتخاب حالت به روزرسانی قیمت
آپلود اکسل جدید
خواندن محصول و قیمت
تطبیق با محصولات قبلی همان فروشگاه
ساخت preview
تایید کاربر
ساخت batch آپدیت
ارسال با Upsert ترب
```

### نتیجه preview اکسل

```text
۸۰ قیمت تغییر کرده
۳۲۰ محصول بدون تغییر
۱۲ محصول نیازمند بررسی
۵ محصول جدید
```

در نسخه اول:

```text
محصول جدید خودکار اضافه نشود.
قیمت خالی یعنی بدون تغییر یا نیازمند بررسی.
قیمت صفر نامعتبر باشد.
```

## Store چرا لازم است؟

الان Submissionها مستقل هستند.

اما برای آپدیت باید بدانیم:

```text
این فایل یا کانال متعلق به کدام فروشگاه واقعی است؟
قبلا برای این فروشگاه چه محصولاتی ارسال شده؟
```

برای همین Store لازم داریم.

مدل پیاده شده:

```text
Store
  id
  name
  seller_phone
  shop_id
  eitaa_channel_id
  eitaa_last_update_id
```

Submissionها به Store وصل می شوند:

```text
Store
 └── Submission
```

در کد فعلی:

```text
app/models.py

Store.eitaa_last_update_id
Submission.store_id
Submission.operation
```

یعنی آخرین `offset` ایتا در همان دیتابیس اصلی محصول ذخیره می شود؛ روی production این دیتابیس Postgres همروش است و روی local معمولا SQLite است.

## آیا StoreProduct لازم است؟

فعلا نه.

قبلا گزینه StoreProduct مطرح شد، یعنی یک جدول جدا برای وضعیت فعلی هر محصول فروشگاه.

اما با طراحی فعلی می توانیم ساده تر جلو برویم:

```text
آخرین وضعیت هر محصول را از BatchItemهای موفق قبلی پیدا کنیم.
```

پس برای v1 آپدیت قیمت:

```text
StoreProduct نمی سازیم.
BatchItem را قوی تر می کنیم.
```

اگر بعدا گزارش گیری یا سرعت سخت شد، StoreProduct را به عنوان جدول summary اضافه می کنیم.

## طراحی آینده BatchItem برای ارسال دقیق

الان وضعیت ارسال در سطح batch ذخیره می شود.

اما پاسخ ترب per-item است:

```json
{
  "created": [
    {
      "index": 0,
      "base_product_rk": "...",
      "prk": "..."
    }
  ],
  "failed": [
    {
      "index": 2,
      "base_product_rk": "...",
      "error_code": "base_product_not_found"
    }
  ]
}
```

پس بهتر است وضعیت هر BatchItem جدا ذخیره شود:

```text
pending
sending
sent
failed
superseded
skipped
```

فیلدهای پیشنهادی:

```text
status
torob_prk
torob_error_code
torob_error_message
sent_at
attempt_count
```

### چرا per-item مهم است؟

اگر یک batch شامل 300 محصول باشد، سیستم آن را در سه request صدتایی می فرستد.

ممکن است:

```text
100 محصول موفق شوند.
100 محصول failed شوند.
100 محصول اصلا ارسال نشوند.
```

اگر فقط وضعیت batch را داشته باشیم، دقیق نمی دانیم کدام محصول چه شد.

با وضعیت per-item:

```text
هر محصول جدا قابل retry، گزارش، و اصلاح است.
```

## latest-wins و superseded

قانون:

```text
برای هر فروشگاه و هر base_prk، جدیدترین قیمت باید برنده باشد.
```

معیار دقیق جدیدترین بودن:

```text
store_id یا shop_id: فروشگاه واقعی
base_prk: محصول واقعی ترب
created_at / id: ترتیب ساخته شدن عملیات در سیستم خودمان
status: معتبر بودن یا superseded بودن آیتم
```

پس latest-wins از روی نام محصول تصمیم نمی گیرد. نام محصول ممکن است کمی عوض شود، مثلا «رب روژین ۸۰۰ گرم» و «رب گوجه روژین ۸۰۰». معیار قابل اتکا این است که هر دو به همان `base_prk` ترب وصل شده باشند.

مثال:

```text
BatchItem قدیمی:
رب روژین = 100000
status = failed

BatchItem جدید:
رب روژین = 120000
status = pending
```

وقتی آیتم جدید ساخته شد، آیتم قدیمی همان محصول برای همان فروشگاه دیگر نباید retry شود.

پس آیتم قدیمی می شود:

```text
status = superseded
```

اما فقط همان محصول.

اگر batch قدیمی این ها را داشته:

```text
رب = failed
شامپو = failed
ماکارونی = failed
```

و batch جدید فقط رب را دارد:

```text
رب = pending
```

نتیجه:

```text
رب قدیمی = superseded
شامپو قدیمی = failed
ماکارونی قدیمی = failed
رب جدید = pending
```

یعنی شامپو و ماکارونی هنوز قابل retry هستند.

## Endpoint Upsert ترب

برای آپدیت قیمت نیاز داریم endpoint ترب این رفتار را داشته باشد:

```text
کلید: shop_id + base_product_rk

اگر نبود: created
اگر بود و قیمت فرق داشت: updated
اگر بود و قیمت همان بود: unchanged
اگر مشکل داشت: failed
```

پاسخ پیشنهادی:

```json
{
  "created": [],
  "updated": [],
  "unchanged": [],
  "failed": []
}
```

یا بهتر:

```json
{
  "results": [
    {
      "index": 0,
      "base_product_rk": "...",
      "status": "updated",
      "prk": "..."
    }
  ]
}
```

## پیام پیشنهادی به ترب

```text
برای قابلیت به روزرسانی قیمت، آیا امکان دارد endpoint فعلی bulk-add رفتار upsert داشته باشد؟
یعنی با کلید shop_id + base_product_rk اگر محصول در فروشگاه وجود نداشت ساخته شود، و اگر وجود داشت فقط price آن آپدیت شود؟
```

بعد از جواب مثبت، سؤال های تکمیلی:

```text
آیا پاسخ per-item برای created / updated / unchanged / failed برمی گردد؟
index در پاسخ نسبت به همان request است؟
اگر timeout سمت ما رخ دهد ولی شما پردازش کرده باشید، روش پیشنهادی برای جلوگیری از تکرار چیست؟
```
